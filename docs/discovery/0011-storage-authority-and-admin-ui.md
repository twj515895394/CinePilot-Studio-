# 第十二轮 Grill：SQLite + Markdown/JSON 的内容权威与 Web UI 读取模型

> 日期：2026-10-30  
> 状态：第十二轮方案 B 已确认；具体跨载体写入策略仍待决定  
> 规范：[grill-with-docs](../process/grill-with-docs/SKILL.md)  
> 依据：[总体需求](./0001-initial-scope-and-design-tree.md)、[第十轮](./0009-agent-handoff-payload.md)、[第十一轮](./0010-controlled-on-demand-retrieval.md)、[ADR-0007](../adr/0007-approved-artifact-revision-policy.md)、[ADR-0011](../adr/0011-mandatory-handoff-context-controlled-retrieval.md)

## 1. 用户已确认与明确提出的实际需求

- Agent 与 UI 都能生成或修改阶段内容，必须经过用户审阅和定稿，旧定稿不可被直接覆盖。
- 一个项目能有多个分集；创意点子和候选方向属于项目但**先于分集建立**。
- 管理后台需要展示已保存/已定稿的创意、故事、剧本、导演方案、镜头/分镜、提示词，支持以项目/分集/阶段/版本查看、编辑、复核、对比。
- Handoff 要小，系统先提供强制约束和准确版本，详细内容通过受控接口按需查询。
- 希望尽可能复用轻量技术，没有建设独立知识库；先前提出 Markdown + JSON + SQLite 是**持久化倾向**，三者的具体唯一权威分工尚未批准。

## 2. 原理：Markdown/JSON 保存内容，不影响后台完整展示

Web UI 不要求所有正文都存储为数据库单元格。后台只需通过**统一业务服务接口**获取可展示的数据：

```text
           ┌────────────── Web UI ────────────────┐
           │ 项目创意池  分集列表  剧本编辑器  镜头树 │
           └──────────────────┬────────────────────┘
                              │ HTTP / API
                    统一业务服务 / 读写校验
                     ┌────────┴──────────┐
                     ↓                   ↓
                SQLite 索引         版本内容文件
               ID/关系/状态           Markdown/JSON
                     └────────┬──────────┘
                              ↓
                按项目 + 内容对象 + 版本组合返回 UI
```

例如分集 EP07 剧本 v3：
1. UI 进入 EP07，接口根据 SQLite 返回“故事 v4 已定稿、剧本 v3 已定稿、导演未开始”等阶段卡。
2. 点击剧本：根据稳定 artifact ID 和 revision 定位 Markdown 剧本文本及 JSON 场次结构（前提是各字段权威归属被明确设计）。
3. UI 将 Markdown 渲染为阅读/编辑界面，将 JSON 中的结构化场次和角色关系渲染为场次目录及属性区；后台可同时显示当前草稿和旧定稿。
4. 点击「修改已定稿剧本」：统一服务创建新的草稿，不编辑旧 v3；用户修改/Agent 修订再确认后形成新定稿。
5. 进入分镜工作台：读取已定稿导演片段与镜头 JSON，呈现树、卡片、镜头列表、提示词；镜头中可引用图片文件或外部资源但首期不要求视频生成。
6. 分集创建之前的点子与创意方向作为项目级内容查询，不依赖先存在 EP07。

## 3. 哪些内容适合哪种展示结构（只是示例，不等于字段设计已通过）

| 领域内容 | UI 体验 | 候选原文/结构载体 | 查找身份与状态 |
|---|---|---|---|
| 创意点子与方向 | 卡片、比较、筛选、详情 | JSON 或 Markdown | SQLite 的项目/对象索引 |
| 故事大纲和文学剧本 | 富文本阅读、场次目录、编辑与差异 | Markdown + 必要结构化 JSON | SQLite 的分集/产物/版本索引 |
| 导演方案 | 章节阅读 + 属性编辑 | Markdown / JSON | SQLite 的阶段、来源、版本 |
| 片段与子片段 | 折叠树、排序、时长和状态 | JSON | SQLite 的分集/版本索引 |
| 镜头和分镜 | 镜头表、卡片、场次来源、提示词 | JSON，图片媒体独立存储 | SQLite 的关系/版本索引 |
| Handoff | 当前阶段摘要、来源版本、查询入口 | 精简 JSON 或受控生成 | SQLite 定位已批准来源 |

注意，媒体图像/参考视频是普通文件或以后对象存储中的资产；SQLite/Markdown/JSON 本身并不能直接代替大图片和视频二进制的存储管理。

## 4. 本轮真正需要决定：唯一事实来源

管理后台可读取三者并不困难；**最危险的是三份数据都能被修改，结果互不一致**。V1 应做到“一个字段只有一个权威载体”，所有修改走受控服务。

### A. SQLite 是所有内容的唯一权威，MD/JSON 仅用于导入导出

- 剧本正文、镜头对象、关系、状态和版本全部在 SQLite。
- 保存时数据库事务容易做一致性；后台查询简单。
- MD/JSON 只是用户可读导出、备份或 Agent 输入快照，并非编辑权威。
- 缺点：Agent/Skill 现有基于文件的创作习惯需要统一适配，直接文件编辑不能作为正式提交；大段文本和文件形式不再是原生权威。

### B. 按数据类型确定唯一权威（推荐）

- **Markdown** 对长篇人类可读内容（故事、剧本叙述、导演阐述）负责；
- **JSON** 对明确结构（创意卡、场次索引、片段/镜头、提示词包）负责；
- **SQLite** 对项目与分集身份、对象关联、版本与审批状态、查找索引负责；
- 绝不允许同一字段在 Markdown、JSON、SQLite 中分别作为可独立编辑的权威。
- UI 和 Agent 经统一业务服务写入；服务保证跨文件与 SQLite 更新具备完整性校验和失败恢复（SQLite 事务无法原子覆盖外部文件）。
- 优点：适合现有 Agent/Skill 文档协作模式，文件易查看、易备份，后台仍可稳定读取；不需要额外知识库。
- 代价：需要仔细设计多载体一致性及恢复机制。是否采用暂存文件、写入日志/操作 ID 等技术需单独细化。

### C. Markdown/JSON 是全部对象及状态的唯一权威，SQLite 完全可重建

- 所有项目、分集、版本、审批、来源关系都写在 Markdown/JSON；SQLite 仅是搜索/列表缓存。
- 优点：纯文件可迁移、可备份，SQLite 损坏后能从文件重建。
- 代价：大量状态/关系变化时文件更新更繁琐，且建立版本一致性与多处编辑规则更难。

## 5. 建议

推荐 B，它以最小额外技术满足 Agent 创作、文件产物可读、Web 管理与按需检索。需要强调：此推荐**不是为同一剧本文本保存三份可以分别编辑的数据**；例如剧本文本由 Markdown 负责，JSON 中不再存一份可修改的重复全文，SQLite 中只保存需要用于定位、展示和查询的 ID、标题索引或派生摘要。

**第十二轮正式结论（2026-10-30，已确认）**：用户选择 **B**——Markdown 为创作正文的权威，JSON 为结构化产物的权威，SQLite 为关系、版本及审批状态的权威；同一字段不允许多处独立写入，UI 与 Agent 必须通过统一业务服务处理读写。已归档 [ADR-0012](../adr/0012-field-owned-markdown-json-sqlite.md)。

这确立的是**逻辑字段的唯一事实来源**，不意味着把同一段剧本全文放进 Markdown 和 JSON 里分别维护，也不意味着 SQLite 的展示索引可被当作正文的另一个修改入口。管理后台能通过 SQLite 定位正确的文件产物和版本，展示创意、剧本、导演和分镜等完整内容。

**下一轮的问题**：当一个产物保存需要同时写入内容文件与数据库元数据时，如何避免断电、程序崩溃造成“索引已更新但文件未保存”的不一致？见 [第十三轮讨论](./0012-cross-store-publish-consistency.md)。

**仍未决定**：具体字段映射、目录和版本文件命名、跨载体发布原子性与恢复、富文本编辑器、数据库 Schema、全文索引、媒体文件、草稿保存粒度与阶段产物合同。
