# 第七轮 Grill：已定稿阶段产物在 UI 或 Agent 中修改时如何保存

> 日期：2026-10-30
> 状态：第七轮方案 B 已确认；第八轮另见后续讨论记录
> 规范：[grill-with-docs](../process/grill-with-docs/SKILL.md)
> 依据：[需求基线](./0001-initial-scope-and-design-tree.md)、[ADR-0004](../adr/0004-screenplay-scene-to-director-segment.md)、[ADR-0006](../adr/0006-project-local-idea-pools.md)

## 为什么优先讨论

用户希望一条分集从点子、创意、故事、剧本到导演、分镜和提示词都由 Agent 对话产出并由用户定稿，之后在 Web UI 查看、操作、编辑、回溯。此前使用 CLI + Skill 缺少系统级历史管理和跨阶段 Handoff，因此**定稿后的修改是否覆盖历史**会直接决定这个产品的核心体验。

本轮只确定修改已定稿阶段产物时的保存语义。细粒度变更影响、数据库字段、自动审批等后续讨论。

## 压力测试

EP03 剧本 v3 已定稿，导演片段与分镜都基于剧本 v3。创作者在 UI 中把 S03 的结尾从「抓到真凶」改成「发现真凶是未来的自己」，随后继续让 Agent 优化分镜。

需要决定旧剧本 v3 是否保留，导演阶段如何知道自己原来引用哪一版剧本。

## 选择

### A：直接覆盖已定稿内容

修改原文件并覆盖原版本，仅保留当前最新结果。实现直观但已无法稳定回溯下游为何如此生成，历史会丢失。与用户的回溯需求冲突。

### B：修改已定稿内容创建新草稿版本，重审后再定稿（推荐）

- 已定稿版本保持可查询、不可被静默覆盖。
- 无论用户从 UI 修改，还是 Agent 生成修订，都在该阶段创建新的草稿版本。
- 用户可继续比较、编辑、让 Agent 优化；确认后才生成新的定稿版本。
- 下游仍能追溯其当初读取的上游版本，并对新版变化提示「待评估」，不直接删除或覆盖下游内容。
- 未定稿草稿的自动保存/临时编辑机制由后续单独设计；此轮只确定已定稿版本不得静默覆盖。

### C：允许手工覆盖，但 Agent 修改强制新版本

看起来更灵活，但同一剧本由 UI 和 Agent 修改时会产生两套行为，对协作和回溯造成不一致。

## 建议

推荐 B。只有保留不可变的定稿历史，前后阶段才能做到可追溯 Handoff。它不要求首期实施重型事件溯源或协同编辑；可以使用轻量版本快照实现。具体如何在 Markdown、JSON、SQLite 中存放，留到数据存储决策。

## 第七轮唯一问题

**第七轮已确认方案 B（2026-10-30）**：不允许直接覆盖已定稿阶段产物，UI/Agent 发起修改均先产生新草稿，用户再次确认后生成新定稿；保留旧定稿及下游原有成果与其上游版本引用。

已同步 [CONTEXT.md](../../CONTEXT.md) 并归档 [ADR-0007](../adr/0007-approved-artifact-revision-policy.md)。

**尚未确定**：草稿自动保存机制、版本粒度、下游重新评估策略以及数据存储实现。下一轮讨论见 [第八轮：上游定稿变化后的下游处理](./0007-upstream-change-impact-policy.md)。
