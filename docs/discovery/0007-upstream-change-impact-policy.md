# 第八轮 Grill：上游新定稿出现后如何处理下游产物

> 日期：2026-10-30
> 状态：第八轮方案 B 已确认；第九轮问题另见后续记录
> 依据：[CONTEXT.md](../../CONTEXT.md)、[ADR-0004](../adr/0004-screenplay-scene-to-director-segment.md)、[ADR-0007](../adr/0007-approved-artifact-revision-policy.md)
> 规范：[grill-with-docs](../process/grill-with-docs/SKILL.md)

## 1. 已确认而且不能退回的前提

- 用户与 Agent 对话生成阶段草稿，用户确认才形成定稿。
- 无论 UI 还是 Agent，都不能静默覆盖旧定稿。
- 下游原有版本及其上游来源版本必须保留，不因上游修订而直接删除或覆盖。
- 剧本场次与导演片段各自有身份，允许同一剧本场次映射多个导演片段。
- 本次**只**选择下游更新与提醒政策；算法、时间线、字段/状态名称不提前定稿。

## 2. 场景压力测试

EP03 的剧本 v3 已定稿，导演方案、片段 P01-P08、分镜及提示词都基于它。
后来用户把 S03 的故事结局调整后定稿成剧本 v4，而其他场次 S01、S02 完全没有修改。

系统如何对待此前依赖 v3 的导演片段与镜头？

## 3. 可选策略

### A. 上游改动后自动重做后续全部阶段

剧本 v4 定稿即自动调用 Agent 从导演、分镜直到提示词批量重做。

优点：总能试图得到基于最新版上游的下游内容。
代价：成本高、打断人工已定稿结果、容易无谓改动、减少用户掌控；与“对话确认后定稿”的产品方式不一致。

### B. 按显式依赖标记“待复核”，用户选择后续动作（推荐）

- 系统保留剧本 v3 和下游既有全部版本，不覆盖它们。
- 新的剧本 v4 定稿后，使用已经保存的**上游版本引用**找出与 v3 有依赖关系的下游产物，将相关内容标记为「待复核 / 可能受影响」。
- 用户在界面中查看差异与关联，自己选择「继续沿用旧版」「让 Agent 更新选中内容」或「进入下一轮修订」等后续动作。
- Agent 修订后仍遵守第七轮规则：创建草稿，用户确认才定稿。
- V1 不要求用 AI 判断每句修改是否真的改变镜头；可以保守标记依赖范围，避免过度设计。
- **跨阶段递归提醒范围**（比如修改一场戏时是否提示所有提示词）以及“继续沿用”的审批规则，后续再细化。

优点：回溯清楚、成本可控、用户主导，支持增量修改和批量剧本先行。
代价：可能标记一些实际无需更改的下游内容，用户需要确认。

### C. 自动语义级差异分析，精确判断哪些镜头要重做

以文本/结构差异、AI 语义分析自动对每个下游镜头计算影响，仅建议重做真正受影响的部分。

优点：自动化程度最高、后期可能提升操作效率。
代价：结果不稳定、难解释，且增加额外 Agent 调用和测试成本；目前尚无准确率验收基线。

## 4. 推荐 B

优先依赖**明确的版本与引用关系**而不是依赖 Agent 的长上下文记忆或复杂语义推断。将“发现关联、展示提醒”作为系统责任；将“是否重做、如何修改、何时定稿”留给用户与 Agent 对话协作。

## 第八轮正式结论（2026-10-30）

**用户选择方案 B（已确认）**：系统以记录的版本依赖关系为依据提示下游「待复核」，已存在的下游内容和旧上游定稿均保留，用户决定沿用还是让 Agent 修订，绝不因为上游出现新定稿而自动重做。该规则已写入 [CONTEXT.md](../../CONTEXT.md)，决策取舍见 [ADR-0008](../adr/0008-review-dependent-artifacts-without-auto-regeneration.md)。

### 此次没有确认的实现细节

- 是否以及如何把「待复核」标记向多个后续阶段传播。
- 继续沿用旧版是否需要人工确认、留痕及具体解除提醒规则。
- 依赖追溯的最小粒度（整阶段、剧本场次、片段、镜头）。
- 「待复核」是否阻止新下游定稿，如何与阶段进入门禁关联。
- Markdown/JSON/SQLite 存储方式及差异比较界面。

这些均留待单独讨论，不把本轮方案 B 解读为自动语义级差异审查。
