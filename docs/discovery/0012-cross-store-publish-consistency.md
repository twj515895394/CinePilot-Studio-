# 第十三轮 Grill：文件与数据库的保存一致性

> 日期：2026-10-30
> 状态：第十二轮 B 已确认；本轮待用户决定
> 依据：[ADR-0012](../adr/0012-field-owned-markdown-json-sqlite.md)、[ADR-0007](../adr/0007-approved-artifact-revision-policy.md)

## 前提

Markdown 负责创作正文，JSON 负责结构化产物，SQLite 负责关系、版本与审批。UI 和 Agent 经过同一个业务服务。定稿版本不可覆盖。

## 压力测试

EP07 的剧本 v3 已定稿，新剧本 v4 需要保存 Markdown 正文、JSON 场次数据和 SQLite 的版本记录。若进程恰好中断，后台不能出现“显示 v4 已定稿，却无法打开文件”；旧 v3 也不能丢失。

## 方案 A：分别直接保存文件和数据库

最简单，但保存到一半崩溃可能导致文件与版本记录不一致；不推荐。

## 方案 B：先写入版本文件，校验后再通过 SQLite 发布（推荐）

1. 先写新版本 Markdown/JSON 文件，不覆盖任何旧定稿。
2. 确认当前版本需要的全部文件已写入并能通过校验。
3. 再通过 SQLite 事务登记该版本的引用和状态，将新版本标为可见。
4. 文件已写完但 SQLite 未提交：旧定稿仍有效，孤立新文件可后续检查清理。
5. 加入基本完整性检查与故障恢复，避免数据库指向缺失内容。

优点：符合单机轻量设计且更可靠，无需引入复杂事务平台。注意 SQLite 与文件系统仍非真正的同一原子事务，持久化与并发细节后续再设计。

## 方案 C：完整跨存储事务协调机制

加入复杂的准备、提交、回滚与恢复状态机。更通用，但当前阶段成本不值得。

## 本轮问题

**是否选择 B：不可变版本文件先写入、校验通过后再通过 SQLite 发布，旧定稿不被覆盖？**

未决定：草稿保存频率、目录规则、并发控制、恢复工具和备份细节。
