# 创作资产体系设计：项目内复用、分集使用与镜头引用

> 版本：0.2（项目基础资产 + 分集变体已确认）  
> 日期：2026-10-30  
> 状态：B2 独立、A3–B4 横向资产管理、**项目基础资产供多分集复用且分集可建立独立变体均已确认**；具体媒体引用和镜头覆盖规则仍为实现建议。  
> 上游：[八阶段合同](./stage-contracts-and-artifact-map.md)、[整体系统总览](./overall-product-workflow-and-system-map.md)、[ADR-0014](../adr/0014-production-breakdown-with-cross-stage-assets.md)、[ADR-0015](../adr/0015-project-assets-with-episode-variants.md)

## 1. 为什么需要一套统一的创作资产体系

同一项目可能有多集独立短视频，反复使用相同的拟人化角色、办公室、道具与视觉风格。若 A3 故事、A4 剧本、B1 导演、B2 拆解、B3 分镜和 B4 提示词各自将角色外观重新写一遍，容易产生漂移；如果全部依赖上下文一次传给 Agent，又回到上下文臃肿的问题。

目标是：**把可识别的设定从一次对话变成有身份、可查看、可引用的项目资产**，让不同阶段按需读取当前任务所用资产，不把所有背景资料都塞进 Handoff。

资产管理是**跨阶段能力**，不是“第九个必须完成的线性阶段”。在 A3 可以创建角色卡，A4 补充情节相关状态，B1 补充表演和视觉意图，B2 核对本集使用清单，B3/B4 以指定资产与约束完成镜头和提示词。

## 2. 已确认的边界

- **B2 是独立的制作拆解阶段**：有自己的正式产物、用户审阅节点和 B2 → B3 正式 Handoff。
- A3–B4 可以逐步创建、完善、引用角色、场景、服装、道具、风格等资产，不能规定“仅 B2 才可维护资产”。
- 项目创意点子和方向与分集的生命周期、镜头叶级归属、来源剧本场次、版本审批、精简 Handoff 与数据存储分工仍遵循既有 ADR。
- V1 不执行实际视频生成；资产可以引用用户导入的图片，不要求每个资产在系统内通过生成 API 产生图像。
- **已确认方案 B**：项目级维护基础角色/场景等资产，同项目不同分集可明确选择或建立造型、服装、状态等局部变体；分集变体不直接改变项目基础设定。
- **未确认的技术细节**：具体关联字段、文件目录和路径策略、版本锁定规则、片段/镜头覆盖的权限与优先级；不得当作已确定的业务规则。

## 3. 候选资产分类与职责

| 资产类型 | 主要资料 | 常见使用阶段 | UI 表现 |
|---|---|---|---|
| 角色 Character | 基础身份、性格/关系、外观、体型、表演特点、参考图、多视图 | A3–B4 | 角色卡、形象参考、使用记录 |
| 场景/地点 Location | 空间、布局、时间/天气/光线基准、画风、参考图 | A4–B4 | 场景卡、图片集、引用场次 |
| 服装 Costume | 外观/材质、适用角色和剧情状态 | B1–B4 | 服装变体卡 |
| 道具 Prop | 外观、所属、剧情用途、状态 | A4–B4 | 道具卡、来源片段 |
| 风格 Style | 视觉画风、色彩、光影、镜头风格原则 | A3–B4 | 项目风格规范 |
| 参考媒体 Reference | 参考图、角色四视图、场景图、分镜图等文件与说明 | A3–B4 | 图片预览、文件附件 |

**剧本场次 Scene**（文学单位）≠**地点场景资产 Location**（视觉/空间设定）≠**导演片段 Segment**（影视拆解单位），即使 UI 中一起展示也必须不同 ID。

## 4. 已确认的项目资产与分集变体关系（以及推荐的镜头引用实现）

~~~text
项目 P
├── 角色资产 R01（项目基础设定）
│    ├── 外观参考图 / 服装关联 / 表情设定
│    └── 资产历史版本 r1, r2, ...
├── 场景资产 L01
├── 道具资产 D01
├── 风格规范 ST01
└── 分集 EP01
     ├── 本集资产使用清单（引用项目 R01，并可选 EP01 造型变体）
     ├── B2 片段 P01 → 剧本场次 S03
     └── B3 镜头 SH01 → 使用的 R01、L01、D01 及其明确版本/变体

同项目分集 EP02
└── 引用同一项目 R01 / L01，可选择独立的 EP02 造型/状态变体
    不直接改写项目级 R01 / L01 基础设定
~~~

### 产品行为已确认，推荐通过稳定 ID 实现

1. **已确认的身份与变体关系**：一名角色的基础身份稳定，但不同分集可以选用不同服装、造型或状态变体；不需要每次换衣服就复制一个“新角色”。
2. **已确认项目基础资产负责基础定义**：相同角色和场景可在同一项目多集引用；此决定不要求跨项目自动共享。
3. **已确认分集显式变体**：EP 可选择项目基础资产或创建本集变体，不直接改写基础设定。具体版本 ID 和选择界面为实现建议。
4. **片段/镜头引用**：片段说明出现的角色与场景，镜头记录实际使用版本及状态；镜头不持有一份重复可编辑的权威角色描述。
5. **引用已定稿而非隐式使用最新版本**：一旦分镜/提示词定稿，它们必须能回溯当时参考的资产版本。是否允许特殊“跟随最新”使用模式留待后续。
6. **文档不等于全上下文**：Handoff 只带本次任务的资产 ID、版本和必须遵守的关键约束；Agent 再按需查询相关角色或场景细节。

### 具体例子

项目“拟人化狗狗短片”有固定角色 R01（警犬拟人形象）。EP01 是办公室故事，R01 穿衬衫、领带；EP02 是科幻故事，同一角色穿未来制服。我们希望保持基础面部/体型一致，并能明确本集服装变体，而不是让两集改变同一份可变角色外观，或让 Agent 根据旧聊天自行猜测。

### 图片资产、图片名称与业务引用：推荐模型（实现建议）

你的理解可以概括为「项目资产库保存参考图片，在各分集/片段/镜头选择实际使用哪张或哪组图」。但**不应让镜头对象直接依赖可变的图片文件路径或文件名**。推荐保留三层信息：

1. **创作资产身份**：如 `CHAR_R01`，代表角色身份及稳定的基础设定。
2. **资产版本 / 分集变体**：如 `R01@rev3`、`EP01_office` 或 `EP02_future`，表达本集采用什么定稿外观/服装状态。
3. **媒体文件**：同一资产或变体可关联 `face_closeup`、`front`、`side`、`back`、`costume_ref` 等多张图片，每张图由稳定 `media_id` 定位，业务服务再映射到实际磁盘相对路径。

~~~text
项目 P-01
├─ CHAR_R01：项目基础角色
│  └─ rev3：脸部特征、体型、基础风格
│     ├─ face_closeup → MEDIA_01 (实际文件在项目资源目录)
│     ├─ front        → MEDIA_02
│     └─ side         → MEDIA_03
├─ EP01：职场故事
│  └─ use CHAR_R01@rev3 + VAR_office
│     └─ costume_ref → MEDIA_11 (西装)
└─ EP02：科幻故事
   └─ use CHAR_R01@rev3 + VAR_future
      └─ costume_ref → MEDIA_21 (未来制服)

EP01 / P05 / SH10 → CHAR_R01@rev3 + VAR_office
                        + face_closeup(MEDIA_01) + costume_ref(MEDIA_11)
~~~

下面是镜头关联的**逻辑示例，不是最终 JSON Schema**：

~~~json
{
  "shot_id": "SH10",
  "character_usage": [
    {
      "asset_id": "CHAR_R01",
      "asset_revision": "rev3",
      "episode_variant_id": "VAR_office",
      "image_roles": ["face_closeup", "costume_ref"]
    }
  ]
}
~~~

实际引用媒体文件时，应从上述 `asset_id/revision/variant` 定位其关联的 `media_id`，由 Python 业务服务映射为可以访问的文件资源。Vue Web / Electron UI 只显示缩略图和资产选择器；Agent 按需请求角色对应的图片列表、指定角色视图或详情。**用户可以看到可读的图片名、路径或标签，但不需要自己反复输入路径。**

推荐交互层级：
- **项目层**：维护基础角色、场景及其图片组；图片文件上传或导入后由服务登记媒体身份。
- **分集层**：选用某个基础资产版本，并选择或创建本集服装/造型变体。
- **片段层**：组织本片段需要哪些角色、场景和道具（待细化）。
- **镜头层**：实际指定本镜头采用哪个角色/变体、哪个外观参考视图；若与分集默认不同则需显式记录（待细化）。

这样既符合用户“分集/片段指定不同图片”的直觉，也不会因重命名文件夹而破坏已经定稿的镜头和 Handoff；同一张项目参考图无需每集再复制一份。资产与媒体文件的生命周期、图片类型枚举和覆盖优先级可在数据/界面设计时确定。

## 5. A3–B4 的资产创作与消费链路

| 阶段 | 可以如何使用资产 | 产物的引用要求 |
|---|---|---|
| A3 故事 | 新增角色、定义关系与性格、草拟世界观 | 记录角色与故事节点关联；视觉细节可逐步完善 |
| A4 剧本 | 明确场次出场人物、地点、重要道具 | 结构化场次引用角色/地点资产 ID，不混淆剧本场次和地点 |
| B1 导演 | 确定角色表演风格、色彩光影、场景视觉重点 | 导演视听规范引用有效风格与相关资产 |
| **B2 拆解** | 核对每个片段需要的角色、地点、服装、道具及缺口 | 正式输出片段/子片段与资产需求及引用清单 |
| B3 分镜 | 按镜头确定人物、地点、服装、表演状态、参考图 | 镜头引用明确资产/版本，避免自由文本重复造身份 |
| B4 提示词 | 按镜头读取必要外观、动作、风格与连续性约束 | prompt 与生成准备包保留资产引用和上游镜头来源 |

## 6. Vue 工作台和 Electron 桌面版如何使用

- **项目级资产页面**：按角色/地点/风格/服装/道具分区，卡片、详情、上传参考图、查看已使用分集（项目级共享为建议，未批准）。
- **分集资产侧栏**：筛选该集使用的资产、查看引用版本、创建/选择当前集变体（变体能力待确认）。
- **B2 制作拆解页**：一侧剧本场次，一侧导演片段/子片段树，中部展示片段需求、未绑定的资产和冲突；允许用户/Agent 补齐后定稿。
- **B3/B4 编辑区**：镜头卡片/提示词面板能打开所引用角色或场景详情；编辑镜头描述不应默默改动共享资产身份。
- **通用版本审查**：资产定义变化后应能追查既有分镜引用的是哪一版，不自动覆盖已定稿分镜。

Python 统一业务服务负责实体/关系/状态，Markdown 负责描述性正文，JSON 负责结构化资产字段，SQLite 负责对象与版本索引；图片作为独立媒体文件由业务服务管理。上述仅是遵循已确认权威分工的草案，不固定具体 Schema、框架和 Electron 本地服务打包方式。

## 7. 为什么不把资产定稿与 B2 完全绑定

- 故事阶段可能早就确定角色身份，剧本阶段可能确定服装状态，导演阶段才建立视觉风格。
- B2 可形成**本集制作资产需求与使用清单**，但不应成为唯一允许创建和审核人物/场景资料的入口。
- 资产不完整时，B2 应展示缺口供用户补充；具体哪些缺口会阻断 B2 定稿，由后续阶段合同和验收标准确定。
- 这样分镜 B3 面对的是有来源的“导演片段 + 资产引用”，而不是难以核验的散乱对话。

## 8. 资产复用方案确认及下一步

**用户已明确选择方案 B（2026-10-30）**：项目级维护角色/场景等基础资产；同一项目的分集能显式建立造型、服装或状态变体，不能直接修改项目基础设定。决策归档见 [ADR-0015](../adr/0015-project-assets-with-episode-variants.md)。

用户进一步询问「是否意味着项目级维护不同图片资产，分集、片段再指定不同图片路径名称」：在操作意义上确实是不同层级选择图片，但工程设计应采用 **资产 ID + 版本 + 分集变体 + 媒体 ID**，而不是直接以路径/文件名作为引用身份。

**下一项整体设计重点**：Agent/Skill 的总体协作与受控数据查询、阶段路由和 UI 任务执行体验。后续再细化图片媒体目录和镜头级覆盖细节，不为这些通用实现细节逐项 Grill。
