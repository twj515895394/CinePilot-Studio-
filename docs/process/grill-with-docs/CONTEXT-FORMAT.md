# CONTEXT.md 格式

## 结构

```md
# {上下文名称}

{一到两句话描述这个上下文是什么以及为什么存在。}

## 术语

**订单**：
{术语的一两句话简洁描述}
_应避免_：购买、交易

**发票**：
交付后发送给客户的付款请求。
_应避免_：账单、付款请求

**客户**：
下单的人或组织。
_应避免_：客户机、买家、账户
```

## 规则

- **要有自己的立场。** 当同一个概念有多个词时，选择最好的一个，将其他的列为应避免的别名。
- **明确标记冲突。** 如果术语有歧义，在"已标记的歧义"中用清晰的解决方案指出。
- **保持定义简洁。** 最多一句话。定义它*是什么*，不是它*做什么*。
- **展示关系。** 使用粗体术语名称并在明显处表达基数。
- **只包含特定于此项目上下文的术语。** 通用编程概念（超时、错误类型、工具模式）即使项目大量使用也不属于这里。在添加术语之前问：这是此上下文独有的概念，还是通用编程概念？只有前者属于这里。
- **当自然聚类出现时将术语分组到子标题下。** 如果所有术语属于一个内聚区域，扁平列表也可以。
- **写一个示例对话。** 开发与领域专家之间的对话，展示术语如何自然地交互并澄清相关概念之间的边界。

## 单一 vs 多上下文仓库

**单一上下文（大多数仓库）：** 仓库根目录的一个 `CONTEXT.md`。

**多个上下文：** 仓库根目录的 `CONTEXT-MAP.md` 列出上下文、它们的位置以及它们之间的关系：

```md
# 上下文地图

## 上下文

- [订单](./src/ordering/CONTEXT.md) —— 接收和跟踪客户订单
- [计费](./src/billing/CONTEXT.md) —— 生成发票和处理付款
- [履约](./src/fulfillment/CONTEXT.md) —— 管理仓库拣货和发货

## 关系

- **订单 → 履约**：订单发出 `OrderPlaced` 事件；履约消费它们以开始拣货
- **履约 → 计费**：履约发出 `ShipmentDispatched` 事件；计费消费它们以生成发票
- **订单 ↔ 计费**：共享 `CustomerId` 和 `Money` 类型
```

技能推断适用哪种结构：

- 如果 `CONTEXT-MAP.md` 存在，读取它以找到上下文
- 如果只有根 `CONTEXT.md` 存在，单一上下文
- 如果两者都不存在，在第一个术语解决时惰性创建根 `CONTEXT.md`

当存在多个上下文时，推断当前主题与哪个上下文相关。如果不清楚，询问。
