## 领域感知

在代码库探索期间，也查找现有文档：

### 文件结构

大多数仓库有一个单一上下文：

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

如果根目录存在 `CONTEXT-MAP.md`，仓库有多个上下文。地图指向每个上下文的位置：

```
/
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                          ← 系统级决策
├── src/
│   ├── ordering/
│   │   ├── CONTEXT.md
│   │   └── docs/adr/                 ← 上下文特定决策
│   └── billing/
│       ├── CONTEXT.md
│       └── docs/adr/
```

惰性创建文件——只在有内容可写时创建。如果没有 `CONTEXT.md`，在第一个术语解决时创建一个。如果没有 `docs/adr/`，在第一个 ADR 需要时创建它。

## 会话期间

### 挑战术语表

当用户使用与 `CONTEXT.md` 中现有语言冲突的术语时，立即指出。"你的术语表将'取消'定义为 X，但你似乎意思是 Y——到底是哪个？"

### 精炼模糊语言

当用户使用含糊或重载的术语时，提出精确的规范术语。"你说的是'账户'——你是指客户还是用户？那是不同的东西。"

### 讨论具体场景

在讨论领域关系时，用具体场景压力测试它们。发明探测边缘情况的场景，迫使用户对概念之间的边界精确。

### 与代码交叉引用

当用户说明某物如何工作时，检查代码是否同意。如果发现矛盾，指出它："你的代码取消整个订单，但你刚说部分取消是可能的——哪个是对的？"

### 内联更新 CONTEXT.md

当一个术语被解决时，直接更新 `CONTEXT.md`。不要批量处理——随发生随捕获。使用 [CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md) 中的格式。

CONTEXT.md 应该完全不包含实现细节。不要将 CONTEXT.md 视为规范、草稿纸或实现决策的存储库。它只是一个词汇表（glossary），别无他用。

### 谨慎提供 ADR

仅当以下三个条件都满足时才建议创建 ADR：

1. **难以逆转**——稍后改变主意的成本有意义
2. **没有上下文令人惊讶**——未来的读者会想"他们为什么这样做？"
3. **真实权衡的结果**——有真正的替代方案，你出于特定原因选择了其中一个

如果任何一个缺失，跳过 ADR。使用 [ADR-FORMAT.md](./ADR-FORMAT.md) 中的格式。
